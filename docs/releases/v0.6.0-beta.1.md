# Cydetix v0.6.0-beta.1

Cydetix `v0.6.0-beta.1` begins the beta release line with the product hardening and beta-readiness
work completed during Alpha.12. It also carries the narrow release-test isolation repair and the
versioned release-evidence architecture added after the immutable Alpha.12 release attempt failed
before publication.

Beta.1 is a prerelease with documented limitations. It is not a stable release, an unrestricted
readiness claim, or an expansion of Cydetix's security or remediation authority.

## Product hardening carried forward

Beta.1 retains Alpha.12's operator-facing output and explainability improvements, `cydetix status`,
readable `explain` output with a structured JSON option, strict MCP request/type boundaries, parser
and scope failure containment, bounded propagation, deterministic corpus expansion, and agent
adapter regression coverage. The public MCP contract remains exactly `cydetix_scan`, `cydetix_fix`,
and `cydetix_explain`.

The conservative corrections to password- and secret-related reasoning remain in place. Incomplete
evidence remains `UNKNOWN`; resource-bounded incomplete analysis remains `TRUNCATED`. Caching and
indexing improvements do not change proof semantics, finding order, or evidence content.

## Release evidence and governance

Release-validation reports are versioned beneath `validation/releases/v<version>/`. Immutable
historical evidence is verified against recorded annotated tag objects and targets, while current
release validation resolves the report for the exact package version and rejects missing, malformed,
wrong-version, stale-source, or contradictory evidence.

The trusted tag-driven workflow derives the npm dist-tag from the package semantic version using a
closed mapping: `alpha.N` publishes under `alpha`, `beta.N` under `beta`, and a version without a
prerelease identifier under `latest`. Unsupported or malformed prerelease identifiers fail closed.
Exact-commit CI, CodeQL, and OpenSSF success are all mandatory release gates.

Microsoft SARIF Multitool remains mandatory for positive and negative SARIF validation. A bounded
second attempt is permitted only after `ETIMEDOUT`; each attempt retains its 210-second ceiling, and
a final timeout or any non-timeout process failure remains a hard validation failure.

The Beta.1 validation report is intentionally not part of the source-preparation commit. Under the
release-evidence contract it may be generated only after this source candidate passes its required
hosted gates, and must then be committed as the sole change immediately following its recorded
source commit.

## Alpha.12 immutable release history

`v0.6.0-alpha.12` remains an immutable failed release attempt. Annotated tag object
`c03f2a1e72af312266f68d66ac4183e0c00511bd` targets `5bf295f53f4ca912a79715fd1ea455a31b72a585`.
Trusted release run `34821381636` failed during the complete verification suite because a positive
development-validation test inherited the release tag environment. Publication was skipped: no
Alpha.12 npm package was published and no public GitHub Alpha.12 release was created. The failure
was release-test isolation, not a newly discovered security-engine defect.

## Readiness and limitations

Alpha.12 recorded the readiness verdict `ALPHA12_BETA_READY_WITH_LIMITATIONS`. Beta.1 carries those
limitations forward rather than erasing or reinterpreting the underlying evidence:

- Broader live-host validation remains incomplete where host access or login was unavailable.
- FastAPI tail-performance evidence remains `INCONCLUSIVE`, not a demonstrated regression or a
  proven improvement.
- Corpus ground truth remains selective and incomplete; no corpus-wide recall or accuracy claim is
  permitted.
- One independently adjudicated lexical false-positive observation remains recorded.
- `UNKNOWN` and `TRUNCATED` remain meaningful proof and completeness states. Thirteen corpus
  repositories were `TRUNCATED` under documented resource or application bounds.
- Absence of findings under incomplete analysis is not proof of security or complete vulnerability
  coverage.

## Compatibility and authority

The four proof states remain `PROVEN_SECURE`, `PROVEN_INSECURE`, `UNKNOWN`, and `NOT_APPLICABLE`.
Confidence, reachability, completeness, and verification remain independent dimensions. Beta.1 does
not broaden SAFE remediation authority; the existing exact session-cookie transformation remains the
only SAFE adapter.

This preparation metadata does not authorize a tag, npm publication, or GitHub release. The trusted
tag-driven workflow and exact-commit release evidence remain authoritative.
