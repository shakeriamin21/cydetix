# Cydetix v0.6.0-alpha.10

`0.6.0-alpha.10` is a release-recovery version carrying the Trust Assurance and Batch 1
functionality already validated in the alpha.8 candidate. It adds no new security rule behavior and
does not begin Batch 2.

## Trust Assurance

The Trust Assurance architecture makes findings proof-carrying rather than assertion-only. Each
supported result records its evidence and proof state, while analysis completeness remains explicit:
missing, bounded, or unsupported analysis is represented as `UNKNOWN`, never silently treated as
proof of security.

Reproducible scan manifests and deterministic catalogue, configuration, suppression, and finding
fingerprints make equivalent scans comparable. Suppression decisions remain visible and auditable
instead of removing findings without evidence.

Remediation authority is constrained by monotonic `maxRemediationClass` ceilings and reason-coded
runtime assessment. `cydetix rules` exposes the admitted rule catalogue, and `cydetix trust` exposes
machine-readable runtime trust state. The existing exact session-cookie adapter remains the only
SAFE transformation. Every Batch 1 remediation ceiling remains `REVIEW_REQUIRED`.

## Batch 1

The bounded source-propagation-control-sink dataflow engine provides high-confidence coverage for
supported SQL injection, OS command injection, path traversal, and server-side request forgery
(SSRF) patterns in JavaScript/TypeScript and Python server contexts. Findings preserve deterministic
evidence, reachability, proof state, fingerprints, completeness, and remediation assessment.

External-corpus validation reviewed 19 pinned repositories without executing target code or
installing target dependencies. Across that reviewed corpus, all 11 actionable external findings
were manually proof-audited and confirmed, with zero confirmed false positives after correction.
Three uncertain flows remained explicitly `UNKNOWN`.

Current documented limitations include bounded or truncated analysis on large repositories,
incomplete cross-file handler and Python framework coverage, unsupported framework/source/sink
patterns, and no proof of custom sanitizer or destination-policy semantics. The exact support
envelope and evidence are recorded in `docs/security/RULE_COVERAGE.md`, `RULE_ADMISSION_GATE.md`,
`TRUST_MODEL.md`, `PROOF_MODEL.md`, `SAFE_FIX_ADMISSION.md`, and
`ALPHA8_EXTERNAL_CORPUS_VALIDATION.md`.

## Release-security recovery

The alpha.9 release attempt exposed an overly broad reviewed-finding validator: it recognized only
the detector, a small path set, and redaction state. Alpha.10 replaces that mechanism with exact,
rationale-bearing review records for all 14 Gitleaks findings and makes the scanner invocation
resistant to repository-controlled configuration, ignore files, and inline allow directives. The
independent scan still covers complete fetched Git history with the same immutable Gitleaks 8.30.1
image and fails closed on every new or changed finding. The full redacted adjudication is in
`docs/security/GITLEAKS_HISTORY_REVIEW.md`.

`v0.6.0-alpha.9` is an immutable failed publication attempt. Release-context validation, exact
hosted CI, OpenSSF verification, and deterministic history audit passed. The trusted release
workflow then stopped at the independent Gitleaks complete-history scan after 14 findings were
reported; the first unreviewed record was in `docs/security/ALPHA8_EXTERNAL_CORPUS_VALIDATION.md`.
The publication job was skipped. No alpha.9 npm package, public GitHub prerelease, release asset,
provenance attestation, or CycloneDX SBOM attestation was created.

`fa048d2f66d337198df9085bfcf1f491eda9dcfd`.
