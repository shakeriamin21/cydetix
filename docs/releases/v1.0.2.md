# Cydetix v1.0.2 maintenance candidate

This document describes the untagged, unpublished `1.0.2` source candidate. It does not authorize or
claim a `v1.0.2` tag, npm publication, npm dist-tag change, GitHub Release, or Marketplace
submission. Stable `v1.0.1` remains the current published release and npm `latest`.

## Maintenance scope

- Reconcile public documentation and immutable release history with the successful `v1.0.1` trusted
  publication while retaining Beta.3 as a historical prerelease and `v1.0.0` as a failed immutable
  attempt.
- Advance package, CLI, plugin, and prepared-publication metadata to `1.0.2` without changing
  dependencies or runtime security behavior.
- Introduce release-validation schema `1.3.0`, which derives alpha, beta, and stable maturity
  verdicts from the existing strict semantic-version channel parser and rejects contradictions.
- Require explicit successful OSV and independent secret-scan state handoff when the trusted
  workflow builds release artifacts; local previews default those checks to `NOT_CHECKED`.
- Continue to parse immutable schema `1.2.0` reports literally for historical verification; do not
  rewrite or reinterpret the `v1.0.1` evidence.
- Document verified and missing GitHub operational controls and define the separate post-V1 field
  validation campaign.

## Stable contract preserved

This candidate does not change detection rules or security-engine behavior, proof-state meanings,
remediation classes or SAFE authority, `.cydetix.json`, the package export boundary, stable schemas,
CLI semantics or exit codes, offline ordinary scanning, repository-code non-execution, or the
three-tool MCP surface (`cydetix_scan`, `cydetix_fix`, `cydetix_explain`).

## Limitations retained

- `UNKNOWN` and `TRUNCATED` remain honest non-proof outcomes. Unsupported, ambiguous, incomplete,
  resource-bounded, or failed analysis never silently becomes `PROVEN_SECURE`.
- Parser, language, framework, call-graph, dependency, resource, and rule coverage remains bounded
  to documented supported patterns. Whole-program and deployed-runtime proof are not claimed.
- External corpus ground truth remains incomplete and selectively adjudicated. No corpus-wide
  recall, completeness, generic accuracy, or zero-false-positive/negative claim is made.
- Resolved dependency inventory remains limited to npm `package-lock` v2/v3. Inventory presence does
  not prove vulnerable-function reachability; PyPI and SPDX inventory are not implemented.
- Secret analysis remains passive, redacted, and intentionally narrow. Live credential validity,
  rotation, revocation, monitoring, and history remediation are not proven.
- SAFE remediation authority remains exactly one bounded session-cookie adapter. Dependency,
  workflow, authentication, authorization, credential-response, and architectural changes require
  review or architectural work.
- Container isolation depends on the trusted Docker daemon, kernel/hypervisor, immutable image, and
  declared runtime controls. The writable ephemeral workspace has no independent byte quota, and
  supported copy/build inputs remain bounded.
- Host UI selection, implicit tool invocation, marketplace behavior, and adapter compatibility are
  best effort. The deterministic CLI/MCP engine remains host-independent.
- Performance evidence remains environment-specific and descriptive. The FastAPI tail-performance
  and truncation cause is unresolved; no cross-host performance SLO or universal large-repository
  performance guarantee is claimed.

## Publication boundary

Development validation may prove only this source state. A future release would still require the
repository's two-commit evidence contract, exact evidence-only diff, exact-SHA hosted CI, CodeQL,
and OpenSSF success, and separate explicit tag/publication authorization.
