# Cydetix v1.0.0 release candidate

This document prepares release notes for the untagged `v1.0.0` candidate. It does not claim that
`1.0.0` has been released, published to npm, assigned to npm `latest`, or made available as a GitHub
release. Beta.3 remains the current immutable published prerelease; Beta.4 was never released.

The candidate carries forward the product behavior audited at
`edd6163bea572d830043659860322c0232453942` and the final `V1_READY_WITH_LIMITATIONS` evidence
committed directly above it. Candidate-only changes are limited to version/release metadata,
documentation, stable release-channel workflow support, focused regression tests, and their
generated artifacts.

## Included V1 scope

- Deterministic offline application-security, authentication, authorization, tenant-isolation,
  secret, dependency, supply-chain, and GitHub Actions analysis within the documented support
  envelopes.
- Stable CLI, structured JSON/SARIF/CycloneDX contracts, exact three-tool local stdio MCP surface,
  and the documented JSON-schema/package export boundary.
- Policy-bounded remediation with unchanged `SAFE`, `REVIEW_REQUIRED`, and `ARCHITECTURAL` meanings.
  The existing explicit-false `HttpOnly` session-cookie adapter remains the only SAFE
  transformation.
- Trusted tag-driven publication with annotated exact-tag validation, exact-commit CI, CodeQL and
  OpenSSF requirements, complete-history/privacy and Gitleaks gates, npm audit and online OSV,
  mandatory Docker verification, checksums, provenance, CycloneDX SBOM attestation, npm OIDC, and
  draft-first GitHub release safety.

## Stable release semantics

The prepared package version is `1.0.0`, its future tag candidate is `v1.0.0`, and its deterministic
npm channel is `latest`. These are candidate metadata only. If a later explicitly authorized
annotated tag is pushed after the new exact candidate SHA passes CI, CodeQL, and OpenSSF, the
trusted workflow will treat stable semantic versions as normal GitHub releases. Alpha and beta
versions remain GitHub prereleases and retain their matching npm channels. Unsupported or malformed
versions fail closed; no `rc` channel is introduced.

## Limitations retained in V1

- `UNKNOWN` and `TRUNCATED` remain honest non-proof outcomes. Unsupported, ambiguous, incomplete,
  resource-bounded, or failed analysis never silently becomes `PROVEN_SECURE`.
- Parser, language, framework, call-graph, dependency, resource, and rule coverage is bounded to the
  documented supported patterns. Cydetix does not claim whole-program or deployed-runtime proof.
- External corpus ground truth is incomplete and selectively adjudicated. No corpus-wide recall,
  completeness, generic accuracy, or zero-false-positive/negative claim is made.
- Resolved dependency inventory is npm `package-lock` v2/v3 only. Dependency presence does not prove
  vulnerable-function reachability; PyPI and SPDX inventory are not implemented.
- Secret analysis is passive, redacted, and intentionally narrow. Cydetix does not validate live
  credentials or prove rotation, revocation, monitoring, or history remediation.
- SAFE remediation authority remains narrow: exactly one bounded adapter exists. Dependency
  upgrades, workflow pinning, authorization/authentication changes, credential response, and
  architectural work remain review-required or architectural.
- Container isolation assumes the trusted Docker daemon, kernel/hypervisor, immutable image, and
  declared runtime controls. The writable ephemeral workspace has no independent byte quota, and
  supported copy/build inputs remain bounded.
- Host UI selection, implicit tool invocation, marketplace behavior, and adapter compatibility are
  best effort. The deterministic CLI/MCP engine remains host-independent, but universal live-host
  behavior is not claimed.
- Performance evidence is environment-specific and descriptive. No cross-host performance SLO or
  universal large-repository performance guarantee is claimed.

## Publication boundary

This preparation creates no tag or release and performs no registry mutation. The next phase is
hosted validation of the exact candidate commit. Only after CI, CodeQL, and OpenSSF succeed on that
SHA may a separately authorized annotated immutable `v1.0.0` tag be created and pushed to trigger
the trusted release workflow.
