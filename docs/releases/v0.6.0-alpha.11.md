# Cydetix v0.6.0-alpha.11

Cydetix `v0.6.0-alpha.11` introduces the validated Batch 2 application-security coverage on top of the immutable successful `v0.6.0-alpha.10` baseline.

This release adds three bounded, proof-carrying production rule families while preserving Cydetix's deterministic trust model, proof states, analysis-completeness semantics, remediation ceilings, resource bounds, and fail-closed behavior.

## Batch 2 application-security coverage

### Context-aware Cross-Site Scripting

Rule:

`AS-XSS-001@1.0.0`

The XSS rule models attacker-controlled data flowing into supported HTML and rendering sinks while accounting for rendering context and recognized security controls.

Supported reasoning distinguishes, within the documented proof envelope:

* HTML body context
* HTML attribute context
* script/JavaScript context
* URL context
* raw HTML rendering

Ordinary React interpolation and autoescaped Jinja value binding are not treated as vulnerabilities when the framework's supported escaping behavior applies.

A recognized escape or sanitizer only proves safety for compatible contexts. Opaque custom sanitizers and unsupported rendering paths remain `UNKNOWN`.

### Open Redirect

Rule:

`AS-REDIRECT-001@1.0.0`

The open-redirect rule identifies supported paths where attacker-influenced data determines a redirect destination without a proven redirect-destination policy.

Recognized controls include narrowly modeled fixed destinations and explicit host/origin allowlists.

Superficial prefix checks are not automatically accepted as security controls because protocol-relative destinations, parser behavior, normalization, and encoding can affect redirect safety.

Unsupported URL-policy wrappers or unresolved destination semantics remain `UNKNOWN`.

### Cross-Site Request Forgery

Rule:

`AS-CSRF-001@1.0.0`

The CSRF rule correlates supported state-changing routes with ambient browser authentication such as cookies or sessions and determines whether a proven anti-CSRF control is present.

Supported controls include explicitly modeled CSRF-token verification, origin validation, and non-ambient authentication.

Bearer-only APIs can be recognized as non-ambient where this is deterministically proven.

SameSite-only evidence, unresolved authentication behavior, opaque middleware, or incomplete browser reachability evidence does not automatically prove security and results in `UNKNOWN` where appropriate.

## Proof and trust model

Batch 2 preserves Cydetix's existing proof states:

* `PROVEN_SECURE`
* `PROVEN_INSECURE`
* `UNKNOWN`
* `NOT_APPLICABLE`

Actionable findings retain deterministic evidence including:

* source
* propagation path
* security-relevant controls
* sink
* route/function context
* proof state
* analysis completeness
* confidence
* reachability
* rule version
* remediation assessment
* catalogue/configuration fingerprints
* bounded evidence path

Incomplete or truncated analysis cannot become `PROVEN_SECURE`.

## Remediation authority

All three Batch 2 rules have a maximum remediation class of:

`REVIEW_REQUIRED`

Alpha.11 introduces **no new SAFE remediation authority**.

Cydetix does not silently invent:

* HTML sanitization strategy
* rendering-context transformations
* redirect destination policy
* redirect allowlists
* CSRF architecture
* authentication architecture

These decisions remain subject to human or agent implementation followed by deterministic Cydetix verification.

The existing monotonic remediation-authority model remains unchanged.

## Security boundaries and limitations

Cydetix continues to operate within explicit bounded proof envelopes.

Examples that may remain unsupported or produce `UNKNOWN` include:

* unsupported template engines
* opaque custom security wrappers
* dynamic routing outside modeled relationships
* arbitrary URL-normalization logic
* browser-specific behavior outside the supported model
* unresolved authentication architecture
* opaque middleware
* whole-program framework behavior beyond analysis bounds
* arbitrary custom sanitizers without deterministic semantics

Cydetix does not interpret the absence of a finding as proof of security when analysis is incomplete.
